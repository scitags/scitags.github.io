Scientific Network Tags

Network flow and packet marking for global scientific computing

SciTags labels data transfers with the science domain and activity behind them. Research and Education networks see how their links are used; science collaborations learn which flows matter to their computing.

How it works

From a transfer request to a dashboard

  1. 01

    Registry

    Maps each experiment and activity to a number, published as JSON.

  2. 02

    Request

    Rucio, FTS, DIRAC or ALICE O2 attaches the tag to the transfer; all four do this in production.

  3. 03

    Marking

    The storage node moving the data (dCache, XRootD, EOS, StoRM) sends fireflies or marks the packets.

  4. 04

    Collection

    Regional collectors run by ESnet, Jisc and GÉANT receive the fireflies and add site and experiment details.

  5. 05

    Insight

    The ESnet Stardust dashboard shows scientific traffic by experiment, activity and site.

Fireflies

A small UDP packet a storage node sends to a collector, describing one flow: its endpoints, experiment, activity and bytes moved. Works on any network today, no router changes needed. The collector name points each site at the nearest regional collector.

udp → collector.scitags.org:10514

Packet marking

The experiment and activity are written into the IPv6 flow label of every packet, so the network can see them in flight.

Get started

Pick your role

I run storage

Turn on fireflies in dCache 11.2.4+, XRootD 5.0+ or EOS 5.2.19+, open outbound UDP 10514, and check your prefixes in CRIC.

# dcache.conf
pool.enable.firefly=true
pool.firefly.destination=collector.scitags.org:10514
Site checklist →

I move data

Pass the tag with Rucio 32.4.0+, FTS 3.12.11+, DIRAC 9.0.8+, gfal2 2.21.0+, xrdcp or an HTTP header.

# scitag = expID << 6 | actID
gfal-copy --scitag 132 <src> <dst>
Transfer services guide →

I run a network

Run the firefly collector: it parses fireflies, adds site and experiment details, and writes to OpenSearch or Kafka, or forwards them on.

input → parse → enrich → output

Software

Open source, on GitHub

flowd-goFlow service in Go: watches sockets, sends fireflies and can mark packets. firefly-collectorSoftware-based UDP firefly collector: parse, enrich and store. firefly-explorerCommand-line tool for looking at fireflies. flowdThe original flow and packet marking service, in Python. go-diagC-binding-free Go API for the kernel's socket subsystem. gbpfA userspace eBPF VM written in Go.

Tagging is also built into dCache 11.2.4+, XRootD 5.0+, EOS 5.2.19+, FTS 3.12.11+, gfal2 2.21.0+, Rucio 32.4.0+, DIRAC 9.0.8+ and ALICE O2, and Pelican support has been merged. StoRM 1.4.3+ sends fireflies through flowd-go; its known issues are under investigation, with an update expected in December 2026.

Demonstrations

Packet marking at terabit speed

Each year at the Supercomputing conference, the SciTags team marks live traffic between research sites with flowd-go, writing the tags into the IPv6 flow label and extension headers.

  1. SC24 · Atlanta

    240 Gbps

    Packet marking between two servers, using the IPv6 flow label and extension headers.

  2. SC25 · St. Louis

    1.1 Tbps

    Three 400 Gbps paths between data transfer nodes at StarLight in Chicago and in St. Louis.

  3. SC26 · Chicago

    1.52 Tbps

    From the University of Victoria to the SC26 exhibition floor in Chicago, against a 1.6 Tbps target.

What's next

Toward the 2027 Data Challenge

The next WLCG Data Challenge, DC27, is planned for early 2027 (currently 22 February to 5 March). Its goal for SciTags is to identify at least 80% of WLCG traffic.

Every storage site

ATLAS is asking every storage site to enable fireflies before DC27. The site checklist covers the steps.

Every prefix in CRIC

About half of today's fireflies cannot be attributed to a site because the site's network prefixes are missing from WLCG CRIC.

More collectors and views

An Asia/Pacific collector is planned, as is a dashboard view that shows each site which of its hosts are sending.
